## 0. 一句话结论

**能用，而且在几个关键体感点上比预期好得多**（PoW 命中时省 8.2 秒、82 万字对话首屏 30.8ms）。
**但有 4 个问题会让第一次用的人卡住**，其中 2 个是「沉默失败」——
点了没反应、没有报错、没有日志，用户只能猜。

| 维度 | 评价 | 依据 |
|---|---|---|
| 首次上手 | **卡** | 无引导、无设置页、身份面板藏在角落 |
| 日常对话 | **顺** | PoW 命中 78.3%，命中时按下回车 0ms 就发出去 |
| 长对话 | **很好** | 107 万字 / 724 条，首屏 30.8ms，全量 604.5ms |
| 出错时 | **清楚** | 10 档状态文案 + 配色全对，关键档位还会拦住发送 |
| 可访问性 | **差** | 会话列表项在 UIA 里只是「两段文字」，键盘 Tab 不到 |
| 可诊断性 | **中** | 有日志，但界面不给入口；沉默失败无提示 |

### 旅程 4 · 接管网页版会话 → 继续发

| 项 | 内容 |
|---|---|
| **预期** | 左栏「未接管」的会话点一下变成「已接管」，能接着聊，上下文不丢 |
| **实际** | 通过。接管后 `remote_count = 8`，锚点校正正确 |
| **问题** | **接管动作本身没有反馈** —— 点下去到列表刷新之间没有任何加载态 |

**可访问性缺陷（这条是硬伤）**：会话列表项在 DOM 里是 `<div class="chat">`，
**没有 `role`、没有 `tabindex`、没有 `data-id`**。后果很具体：

- 51 个会话项在 UIA 里全部只以 `ControlType.Text` 出现（只是两段文字）
- 没有 `InvokePattern`，`Invoke()` 无从调用
- 没有 `AutomationId`，`Find(...)` 无从定位
- **屏幕阅读器读不出「这是可点的会话项」**
- **键盘用户无法 Tab 到它**

WPF 壳用原生控件没有这个问题。这是 Web 壳独有的退化。

### 旅程 6 · 连续快速发送 → PoW 预取命中率

| 项 | 内容 |
|---|---|
| **判据** | 命中率、命中时 `pow_ms` 严格为 0、命中轮 `solve_ms > 0` |
| **实际** | **全部通过** |

实测数据（2026-10-18 22:38 重跑，全量 184 份引擎日志）：

| 指标 | 基线（无预取） | 预取生效后 |
|---|---|---|
| 事件数 | n=184 | n=23（命中 18 / 未命中 5） |
| `challenge_ms` 中位 | 150.9 ms | **命中时 0.0 ms** |
| `pow_ms` 中位 | **8242.8 ms** | **命中时 0.0 ms** |
| `solve_ms`（后台） | — | 中位 3572.5 ms |
| 命中率 | — | **78.3%** |
| 末尾连续命中 | — | **17 轮 / 共 23 轮** |

**用户体感**：基线每轮要干等 **8.2 秒**；命中时按下回车 **0 秒**就发出去。

`★ 这里有个容易误读的字段`：`pow_ms` 和 `solve_ms` 语义刻意不同 ——

所以「cached=True 但 solve_ms=10607」不是自相矛盾，**恰恰是设计意图**：
那 10.6 秒被挪到了用户看不见的后台。

### 旅程 7 · 超长对话 → UI 是否掉帧

| 项 | 内容 |
|---|---|
| **样本** | `20261015-232516-4504.json` —— **1624 KB / 724 条 / 107 万字 / 单条最长 40887 字** |
| **实际** | 全部通过 |

| 指标 | 实测 | 判据 |
|---|---|---|
| 首屏（推完） | 0.7 ms | — |
| **首屏（排完版）** | **30.8 ms** | ≤ 600 ms |
| 全量铺完 | **604.5 ms** | ≤ 10000 ms |
| DOM 节点 | 600 个 | ≤ 600（产品上限） |
| 滚到底后贴底 | 差 0 px | 贴底 |
| 回滚中位帧间隔 | 16.7 ms | ≤ 20 ms |
| 回滚 >50ms 长帧 | **0 帧** | 0 |
| 回滚后总高膨胀 | +0.8% | ≤ 5% |

**这是本产品最强的一项**：107 万字的对话，首屏 30.8 毫秒。

#### `content-visibility` 的实测裁决

CSS 里给消息块加了 `content-visibility: auto`，注释声称「600 块首屏 134ms → 4.7ms」。
本轮做了 A/B 对照，结论是**这条规则有真实收益，但收益的位置和注释说的不一样**：

| 场景 | 开启 CV | 关掉 CV | 结论 |
|---|---|---|---|
| 批量插入 600 块 · 强制同步布局 | **22.3 ms** | 304.1 ms | **快 13.6 倍，收益真实** |
| 滚动帧间隔中位 | 16.7 ms | 16.7 ms | 无差异 |
| 滚动最长帧 | 19.3 ms | 17.0 ms | 开启**略差** 2.3ms |
| 滚动 >50ms 卡顿帧 | 0 帧 | 0 帧 | 两者都不卡 |

**判读**：CV 省的是「一次性灌大量块」的成本，不是滚动成本。
滚动时它反而让最长帧多了 2.3ms（仍远低于 50ms 卡顿线）。
**规则该留，但注释里「首屏 134→4.7ms」的说法不准确** —— 实测首屏是 30.8ms，
且分批铺开之后首屏本来就不含全部 600 块。

## 2. 本轮发现并修复的缺陷

### 缺陷：`show_thinking` 被说成「切换会话形态」

**现象**：每次切换「显示思考过程」开关，聊天流里都会插入一条：

> 已切换会话形态 · 一般对话（写入 DeepSeek 历史）· 思考模式 · 联网开

**问题**：`SetChatAsync` 收到四个参数，其中三个是**会话形态**，一个是**纯本地显示开关**：

| 参数 | 真实语义 | 影响上游？ |
|---|---|---|
| `temporary` | 临时对话（不写入历史） | 是 |
| `extended_thinking` | 上游是否思考 | 是 |
| `search_enabled` | 是否联网 | 是 |
| **`show_thinking`** | **本地是否显示思考原文** | **否** |

引擎侧注释写得很清楚：

```python
# 思考过程是否显示。**纯本地显示开关**，下一轮生效，不改上游行为 ——
# 「上游是否思考」由 `extended_thinking` 管，两者别混。
```

把它并进「已切换会话形态」这句话里，用户会以为**自己切换了对话类型**——
实际只是隐藏了一段文字。已累积 9 条误导性通知。

**修复**（`shell/DeepSeekAgent.Desktop/AgentHost.cs` 的 `SetChatAsync`）：
把四种配置拆成两条互斥分支 —— 会话形态说形态，显示开关只说自己影响显示。

**验证**：重新编译 0 Warning / 0 Error，重启壳（PID 18780），实测切换只出 1 条
「已隐藏思考过程（只影响本地显示，不影响上游是否思考）」。

## 3. 新建的门禁：Web 壳双向消息契约

### 为什么 WPF 壳不需要这道门禁

WPF 壳的「前端」是 C# 自己写的：按钮直接绑方法，**编译器会拦下拼错的成员名**。

Web 壳的前端是 JS，跟宿主之间只有**字符串**：

```
JS:  send({ t: 'switchConv', id: ... })     → postMessage
C#:  switch (type) { case "switchConv": ... }
```

字符串拼错，编译器一个字都不会说。用户看到的是「点了没反应」——
**没有异常、没有日志、没有红色，只有沉默**。

### 两个方向都查

| 方向 | 后果 |
|---|---|
| 前端发了宿主不认识的 `t` | 消息石沉大海（改名时只改一边） |
| 宿主发了前端不认识的 `t` | 数据到了但界面不更新（**更阴险**：用户以为功能坏了） |

### 实测结果

```
宿主接受 31 种 · 前端发送 28 种
宿主发送 16 种 · 前端接受 16 种

[方向一] 前端发送 → 宿主接受   [通过] 无孤儿消息
[方向二] 宿主发送 → 前端接受   [通过] 无孤儿消息

[参考] 推送型（宿主主动发，前端不该主动请求）
         · idLabel
         · models
         · refreshConvs

[通过] 双向契约一致
```

### 门禁本身的三次纠错（教训比结论更值得留）

| 版本 | 误报 | 根因 | 修法 |
|---|---|---|---|
| 第 1 版 | 5 个假孤儿（err/files/ready/idres/idstate） | 全是**注释里**的说明文字 + `mock.js` 模拟宿主的 `fire()` | 加 `strip_comments()`，排除 mock.js |
| 第 2 版 | 入站集合被撑到 14 种无关项 | 全局扫 `case 'x'` 把 transcript kind 分派也算进来了 | 加 `RE_HANDLE`，只扫 `handle(m)` 函数体 |
| 第 3 版 | `models` 被误判为死代码 | 没看出它是**宿主推送** | 加 `PUSH_ONLY` 集合 |

第 3 版这条特别值得记：我一度认定是真缺陷，准备去修 ——
实际 `WebBridge.cs:262` 在 `case "hello"` 里已经 `_ = RefreshModelsAsync()`，
握手完就把列表推下来了。**推送型消息不该要求前端主动发。**

**运行时交叉验证**：门禁说 `models` 是推送型 → 去页面看 `selModel`，
实测 2 个选项、当前选中 `default` —— 宿主确实推了、前端确实画了。

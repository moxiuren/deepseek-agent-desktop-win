# Gemini 封控评估 —— 把 Gemini 后端内置进 deepseek-agent-desktop 之后，风险到底有多大

> **结论先行**：
>
> 1. **访客模式的账号连坐风险是 0** —— 不登录，没有账号可封。这是本档位最重要的性质。
> 2. **账号模式的风险不是「会不会被封」，而是「cookie 会不会掉」** —— 26.5 小时真实数据里
>    `blocked` 为 true 出现 **0 次**，`rate_limits` 非零出现 **0 次**，`abuse_clean` 为 false
>    出现 **0 次**。真正的故障是 289 次 `1016 未认证`，性质是**本地 cookie 缓存失效**，不是封号。
> 3. **Gemini 侧有 DeepSeek 侧没有的东西：主动预警通道。** 三个 RPC 能在发请求**之前**
>    读到账号状态、abuse 状态、额度水位。DeepSeek 侧一个都没有（见 `engine/gad_engine/circuit.py` 头部）。
> 4. **本项目已经把心跳接管了** —— 空闲时 0 流量，不会因为「挂着不用」而被当成异常。
>
> 实测日期：2026-10-19 · 证据目录：`%LOCALAPPDATA%\Gemini-Agent\logs\`

---

## 一、先把「封控」拆成三件不同的事

日常说的「封号」其实是三个独立机制，混在一起谈会导致误判。Gemini 侧三者的可观测性完全不同：

| 机制 | 表现 | 能否事前看到 | 本项目能否防 |
|---|---|---|---|
| **① 账号级封禁 / 停用** | 登录态直接失效，所有请求 401/403 | ✅ 能，`otAQ7b` 返回非 1000 | 部分（访客模式可完全规避） |
| **② 限流（rate limit）** | 请求被拒或降速 | ✅ 能，`pacing.rate_limits` 计数 | ✅ 能，内置退避与节拍 |
| **③ 滥用标记（abuse）** | 未必立刻失败，但会进观察名单 | ✅ 能，`GPRiHf` 返回 `is_clean` | ✅ 能，命中即冻结 |

**关键点**：这三项在 Gemini 侧**全部可主动查询**。这是它比 DeepSeek 侧好处理得多的根本原因 ——
DeepSeek 侧只能从 HTTP 状态码反推，而 `401` 无法区分「token 过期」与「账号被处置」
（详见 `circuit.py` 的「必须说清的三件事」）。

## 二、两种模式，风险量级差一个数量级

### 2.1 访客模式（`identity.guest_mode = true`）

代码路径（`engine/gad_engine/transport/gemini_rpc.py`）：

```python
# :277 —— 访客模式根本不加载本地 cookie
if not self.identity.guest_mode:
    self._cookies = load_cookies(self._resolve_cookie_file())

# :302 —— 匿名客户端，不传任何凭据
if self.identity.guest_mode:
    client = GeminiClient("", "", proxy=self.identity.proxy or None)

# :326 —— 不轮换 cookie（本来就没有）
auto_refresh=not self.identity.guest_mode,
```

**结论：账号连坐风险 = 0。**

这不是「风险很低」，是**结构上不存在**：请求里没有任何身份信息，服务端看到的是一台
匿名设备。即使行为异常被处置，处置的对象也是一个匿名会话，与 `<gemini-account>@example.com`
这个账号没有任何关联通道。

**代价**（必须一并说清，不能只讲好处）：

| 代价 | 具体表现 |
|---|---|
| 只有 `gemini-flash-lite` | 上游对匿名会话只开放轻量模型，能力显著弱于 `gemini-argon` |
| 1016 是常态 | 上游恒返回 `UNAUTHENTICATED`。代码在 `:516` 特判，否则会被熔断器当成故障连击 3 次直接停机 |
| 会话不可续 | 匿名会话的生命周期不由我们控制 |

`:516` 那行特判是访客档能用的前提，值得单独强调：

```python
# 访客模式下上游恒返回 1016（未认证），那是**正常态**而不是故障。
# 不特判的话，`Agent` 会把 1016 当成 auth 失败喂给熔断器，
# 连续 3 次就停机 —— 表现是「引擎刚起来就说自己被封了」。
if self.identity.guest_mode and parsed is AccountStatus.UNAUTHENTICATED:
    status.account_status_text = "访客模式（未登录）"
    status.account_status_short = "访客"
```

### 2.2 账号模式（`guest_mode = false`）

用真实 cookie（`__Secure-1PSID` + `__Secure-1PSIDTS`）登录。风险结构完全不同：

- **有账号可连累** —— 这是全部风险的来源
- 但**有完整的事前可观测性** —— 三个 RPC 能提前看到状态
- 而且**历史数据显示这个账号从未触顶**

## 四、主动预警通道：Gemini 相对 DeepSeek 的核心优势

上游 `gemini_webapi` 暴露四个状态 RPC（`constants.py:126-130`）：

| 常量 | RPC id | 用途 |
|---|---|---|
| `GET_USER_STATUS` | `otAQ7b` | 账号状态码（1000 可用 / 1016 未认证） |
| `GET_ABUSE_STATUS` | `GPRiHf` | 滥用标记（`is_clean` / `signal`） |
| `CHECK_GEMINI_QUOTA` | `qpEbW` | Gemini 额度 |
| `CHECK_QUOTA` | `aPya6c` | 通用额度 |

本项目的取用方式（`gemini_rpc.py` 的 `health()`）：

```python
raw_status = int(getattr(client, "account_status", 0) or 0)
parsed = AccountStatus.parse(raw_status)

abuse = getattr(client, "abuse_status", None)
if isinstance(abuse, dict):
    status.abuse_clean = bool(abuse.get("is_clean", True))
    status.abuse_signal = abuse.get("signal")

ratio, detail = _extract_quota(getattr(client, "quotas", None))
status.quota_used_ratio = ratio
```

**这三个值的意义是「事前刹车」**：在发出任何一条用户请求之前，`health()` 就已经知道
账号是否可用、有没有被标记、额度还剩多少。对比 DeepSeek 侧 —— 只能等 401/429/`Server busy`
回来才知道出事（见 `circuit.py` 头部对能力缺口的坦白）。

### 4.1 一个必须说清的边界：abuse 查询失败 ≠ 被封

`engine-20261014-223257.log` 里有一处容易误读的日志：

```
22:32:59.020 [err] WARNING  | gemini_webapi.client:_parse_rpc_results:504
                 - RPC request GPRiHf failed: Permission denied or unauthenticated.
22:32:59.020 [err] SUCCESS  | gemini_webapi.client:init:346
                 - Gemini client initialized successfully.
```

**同一毫秒内，`GPRiHf`（abuse 查询）失败，而客户端初始化成功。**

这说明：未认证态下 abuse 查询会被拒，那是**权限问题**，不是「你被标记了」。
如果把 `GPRiHf` 失败当成封控信号，会得到一个完全错误的结论。

代码里对应的正确处置是 `abuse_clean = null`（未知），而不是 `false`（有标记）——
`null` 与 `false` 在语义上必须分开，这正是 `abuse_clean` 用三态而非布尔的原因。

## 五、掉登录 ≠ 封号：一次完整的事故复盘

这是整份评估里最值得记的一段，因为它演示了**如何区分两种看起来一样的故障**。

### 5.1 现场（`engine-20261014-223257.log`，第 4-8 行）

```
22:32:58.685 WARNING | client:_fetch_user_status:559
  - Account status: UNAUTHENTICATED - Session is not authenticated or cookies have expired.
    Please check your cookies.

22:32:58.686 DEBUG   | client:_fetch_user_status:571
  - Cached cookies produced an unauthenticated session; clearing them so the next
    attempt can fall through to the supplied credentials.

22:32:58.686 DEBUG   | utils.rotate_1psidts:clear_cookies_cache:116
  - Cleared cached cookies at ...\cookie-cache\.cached_cookies_g.a000Dgm...json

22:32:59.020 WARNING | client:_parse_rpc_results:504
  - RPC request GPRiHf failed: Permission denied or unauthenticated.

22:32:59.020 SUCCESS | client:init:346
  - Gemini client initialized successfully.
```

### 5.2 因果链

1. 上游读**缓存 cookie** → 得到未认证会话（`1016`）
2. 上游判断「缓存坏了」→ **主动清空缓存**
3. 清空后回退到**我们文件里提供的凭据** → 重新初始化
4. `init` 返回 **SUCCESS**

**全程 2 秒，自愈。** 没有人工介入，没有重新登录。

### 5.3 判据：怎么区分掉登录与封号

| 特征 | 掉登录（本次） | 账号被封 |
|---|---|---|
| 清缓存后重试 | ✅ 成功 | ❌ 仍失败 |
| `otAQ7b` 返回码 | 1016（未认证） | 非 1000 且非 1016（如被停用） |
| `GPRiHf` | 可能失败（权限问题） | 可能返回 `is_clean: false` |
| 持续时长 | 秒级，自愈 | 持续，不自愈 |
| 日志里的关键动词 | `clearing them so the next attempt can fall through` | 无此句 |

**核心判据是第 1 行**：清缓存后能否恢复。能恢复 = 本地缓存问题；不能恢复 = 才需要考虑封号。

本项目已经把「保持 cookie 文件新鲜」做进了 `_persist_rotated_cookies()`，让第 3 步
从「回退到一个还能用的值」变成常态 —— 死循环从「必然」变成「可自愈」。它的两个安全约束值得记住：

```python
#   * 只在账号可用时写 —— 否则会把一个刚被拒的坏值固化下来；
#   * 值没变就不写盘 —— 轮换约 10 分钟一次，没必要每次都动文件。
```

## 六、流量画像：为什么 Gemini 侧的请求量比 DeepSeek 侧小得多

这是架构差异带来的**结构性优势**，不是调优结果。

| 维度 | DeepSeek（`deepseek_rpc`） | Gemini（`gemini_rpc`） |
|---|---|---|
| 每轮请求数 | 1（但 payload 随上下文增长） | 1 |
| 上下文携带方式 | **每次重发全文**，O(n) | 服务端凭 `cid`/`rid`/`rcid` 持有，O(1) |
| 长对话时的流量 | 线性增长 | 恒定 |

`gemini_rpc.py` 文件头的原话：

> 与 DOM 注入（T1）的本质区别：不经过页面渲染，直接读 SSE 流。因此没有
> 「代码块识别」这一整类 bug，无需回填输入框、无需三级定位发送按钮；
> 上下文由服务端凭 cid/rid/rcid 持有，payload 从 O(n) 降到 O(1)。

**对封控的意义**：服务端看到的请求体积不随对话长度膨胀，少了一类「异常流量」特征。

### 6.1 DeepSeek 侧的对照数据（同一台机器，同期）

```
$ wc -l sends-2026101*.jsonl
  sends-20261017.jsonl: 14
  sends-20261018.jsonl: 63
  sends-20261019.jsonl: 156
  三天合计: 233

$ grep -oh '"http_status": *[0-9]*' requests-*.jsonl sends-*.jsonl | sort | uniq -c
   77 "http_status": 200      ← 全部 200，无 429 / 401 / 403
```

> **取证纪律提示**：初次 grep `429|401|403` 时命中 1 条，看似有问题。核查后发现是
> `"ms": 429.6` 里的**毫秒数**被误匹配，不是 HTTP 状态码。**统计日志时必须锚定字段名，
> 不能裸搜数字** —— 否则会把正常数据读成故障，进而做出错误的处置。

## 七、本项目已经做了哪些防封措施

| 措施 | 实现位置 | 作用 |
|---|---|---|
| **心跳接管** | `_apply_background_policy()`，`activity_task` 三处 | 空闲时**主动停掉**上游的心跳任务，0 流量 |
| **节拍控制** | `PacingConfig`：`base_gap_ms=2500`、`sigma=0.55`、`max_burst=2`、`hold_after_burst_ms=12000` | 请求间隔带随机抖动，不呈现机器节拍 |
| **阅读停顿** | `read_pause_every=6`、`read_pause_min_ms=4000` | 每 6 轮插入一次 4-9 秒停顿，模拟人在读输出 |
| **活跃时段** | `active_start_hour=8` / `active_end_hour=24` | 凌晨不发请求 |
| **会话轮换** | `max_turns_per_session=40` | 单会话不超过 40 轮 |
| **主动遥测** | `health()` 读 `otAQ7b` / `GPRiHf` / `qpEbW` | 发请求前就知道账号状态 |
| **熔断分层** | `circuit.py`：`auth_backoff` / `temporary_unavailable` / `abuse_freeze` / `quota_slowdown` | 不同故障不同处置，不搞一刀切停机 |
| **cookie 自愈** | `_persist_rotated_cookies()` | 轮换值写回文件，避免隔夜掉登录 |
| **凭据权限** | `os.chmod(path, 0o600)` | 明文 cookie 等同密码，只允许本人读写 |

### 7.1 关于「`maintenance.enabled=False` 会不会导致掉登录」—— 一个已澄清的误解

`MaintenanceConfig.enabled` **只管心跳，管不到 cookie 轮换**。2026-10-19 源码核实：

- `gemini_rpc.py` 全文只碰 `activity_task`（三处：453 读 / 459 建 / 463 取消）
- **`refresh_task` 一次都没有出现**
- 轮换由 `_ensure_client()` 里的 `init(auto_refresh=...)` 控制，实参只跟 `guest_mode` 有关

所以：**Gemini 档位下把 `enabled` 设成 False（默认值）不会导致隔夜掉登录。**
真会掉登录的是 `guest_mode` 切换 —— 访客本来就没有 cookie。

这一点曾在本项目里被误读成「配置隐患」，现已在 `MaintenanceConfig` 的注释里写死，防止再踩。

## 八、风险矩阵与操作建议

### 8.1 分场景结论

| 场景 | 账号连坐风险 | 可用模型 | 建议 |
|---|---|---|---|
| **只想试试，不打算登录** | **0** | `gemini-flash-lite` | ✅ 首选。直接开访客模式 |
| 日常使用，能接受偶尔掉登录 | 低 | `gemini-argon` 等全部 | ✅ 可用。掉登录会自愈，见第五节 |
| 高频批量任务 | 中 | 全部 | ⚠️ 需盯 `quota_used_ratio`，历史峰值已 75% |
| 无人值守长期挂机 | 低 | 全部 | ✅ 心跳已接管，空闲 0 流量 |

### 8.2 操作红线

1. **不要用主号** —— 这是 `IdentityConfig.require_dedicated_account` 存在的全部理由。
   即使历史数据零封控，也不该拿日常账号去赌。
2. **不要关掉节拍控制** —— `base_gap_ms` 调到 0 会让请求变成机器节拍，
   这是最容易被识别的特征。
3. **不要把 `active_hours` 设成 24 小时** —— 人类不会全天候均匀发请求。
4. **看到 1016 不要慌** —— 先看日志里有没有 `clearing them so the next attempt can fall through`。
   有 = 本地缓存问题，会自动恢复。

### 8.3 什么时候该真正停手

按严重程度递增：

1. `rate_limits` 计数开始增长 → 放慢节拍，不必停
2. `quota_used_ratio` 超过 0.85 → 自动降速 3 倍（已有）
3. `abuse_clean` 变成 `false` → **立即冻结 24 小时**（`abuse_freeze_ms`）
4. `otAQ7b` 返回非 1000 且非 1016 → **停机，人工介入**（`hard_stop_ms`）
5. 清缓存 + 重新登录后仍然 401 → **才考虑封号**

## 九、未验证 / 存疑的部分

诚实列出，不当作已证：

1. **历史数据来自 `gemini-agent-desktop`（另一个项目），不是本项目。**
   本项目的 `gemini_rpc.py` 是从那边移植的，协议层一致，但**本项目自己的 Gemini 档位
   尚未跑过长时间真实流量**。上面的 26.5 小时数据只能证明「这套协议 + 这个账号」的
   封控表现，不能直接等价为本项目当前实现的表现。
2. **访客模式的实际可用性未做长跑验证。** 代码路径与 1016 特判已通过单元测试
   （`test_gemini_transport.py`，用 fake client 离线跑），但真实匿名会话的稳定性、
   限流策略、会话存活时长都没有实测数据。
3. **`quota_used_ratio = 0.75` 这个稳态值的语义未确认。** 是「某短窗口的稳态占用」
   还是「累计额度已用 75%」，需要读上游 `_extract_quota` 的窗口定义才能定论。
   本文件按保守解释处理（当作余量 25%）。
4. **`abuse_clean = null` 的 294 条未逐条归因。** 合理推测是未认证态下查询被拒
   （见 4.1），但没有逐条核对。
5. **没有做过「故意触发限流」的测试。** 上面所有结论都是「正常使用下没出事」，
   不是「压力下会怎样」。若要做，必须在访客模式下做 —— 账号模式不做这种测试。

## 十、一句话总结

**访客模式的风险是零，代价是模型弱；账号模式的风险是「偶尔掉登录」而非「被封」，
且掉登录会自愈；真正的危险信号（abuse / quota / 非 1016 的状态码）Gemini 全部
提供主动查询通道，本项目已经接上了。**

比起 DeepSeek 侧「只能等 401 回来才知道出事、而且 401 还分不清是过期还是被封」，
Gemini 档位在**可观测性上反而更强**。

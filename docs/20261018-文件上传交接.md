## 2. 完整协议（已逆向，可直接实现）

### 2.1 核心结论：**发一个文件 = 两次 PoW**

这是最容易踩的坑。上传文件本身也要解一次 PoW，而且 `target_path` 不同：

```
第一次 PoW: target_path = "/api/v0/file/upload_file"      ← 上传用
第二次 PoW: target_path = "/api/v0/chat/completion"       ← 发消息用
```

两个 PoW **不能互相复用**（payload 里的 `target_path` 参与签名）。

### 2.2 接口常量

```js
let cV = "/api/v0/chat/completion",
    cW = "/api/v0/file/upload_file";
```

### 2.3 上传函数（原文）

```js
async function cz(e, t) {
  let { file: n, headers: r } = e;
  let { onUploadProgress: s, abortSignal: a } = t;
  let o = new FormData();
  o.append("file", n);
  return (await http.post(cW, {
    body: o,
    onUploadProgress: s,
    signal: a,
    headers: r
  })).json;
}
```

**要点**：
- `multipart/form-data`，字段名 **`file`**
- **不要手写 `content-type`** —— 必须让 HTTP 库自动生成 boundary
- 返回的是**原始 JSON**（`.json`）

#### 1.2 新增 `_upload_file`

```python
UPLOAD_PATH = "/api/v0/file/upload_file"

def _upload_file(self, s, token: str, referer: str, path: str,
                 *, thinking: bool, model: str) -> dict:
    """上传一个文件，返回 biz_data（含 id / status / file_name / file_size）。"""
    p = Path(path)
    data = p.read_bytes()

    # ① 上传也要 PoW，target_path 不同
    ch = self._fetch_challenge(s, token, referer, target_path=UPLOAD_PATH)
    solved = solve(ch, UPLOAD_PATH, workers=self._workers)
    pow_header = base64.b64encode(json.dumps(
        {k: v for k, v in solved.items() if not k.startswith("_")},
        ensure_ascii=False, separators=(",", ":")
    ).encode("utf-8")).decode("ascii")

    headers = self._headers(token, referer)
    headers["x-ds-pow-response"] = pow_header
    headers["x-thinking-enabled"] = "1" if thinking else "0"
    headers["x-model-type"] = model
    headers["x-file-size"] = str(len(data))
    # ★ 不要设 content-type —— 让 curl_cffi 自动生成 boundary
    headers.pop("content-type", None)

    resp = s.post(
        BASE + UPLOAD_PATH,
        headers=headers,
        files={"file": (p.name, data)},   # 字段名必须是 file
        timeout=self._timeout,
    )
    self._raise_for_status(resp, "upload_file")
    body = resp.json()
    self._raise_for_biz(body, "upload_file")
    biz = (body.get("data") or {}).get("biz_data") or {}
    if not biz.get("id"):
        raise TransportError(f"上传响应缺 id：{body}", config=True)
    return biz
```

**注意 `_raise_for_biz`** 可能只认 `code`，要看它是否也检查 `data.biz_code`。
上传响应是 `{code:0, data:{biz_code:0, ...}}`，与 completion 同构。

#### 1.4 缓存分池（重要）

`engine/gad_engine/pow_cache.py` 现在只缓存 `COMPLETION_PATH` 的结果。
上传用的是 `UPLOAD_PATH`，**不能混用**。

- **B**：`PowCache` 改成 `dict[target_path] -> cache`，两池独立预取。

**选 A 最简单**，第 1 步就这么做。

## 5. 坑清单（按踩到的概率排序）

1. **上传也要 PoW，且 `target_path` 不同** —— 忘了这条会直接 403。
2. **两个 PoW 不能复用** —— `target_path` 参与 base64 内容，缓存池不能混。
3. **`content-type` 必须让 HTTP 库自动生成** —— 手写 `multipart/form-data`
   会缺 boundary，服务端解析失败。
4. **字段名是 `file`**，不是 `files` / `upload`。
5. **`x-file-size` 是字节数**，不是 KB/MB。
6. **`ref_file_ids` 是数组**，不是字符串；空数组也要带（`[]`）。
7. **「Text extraction only」** —— 发 PDF 得到的是文本，不是原文件。
8. **100MB / 50 个** 是默认值，实际从 `file_feature` 取，可能更小。
9. **WPF 旧壳的「附件」不能抄** —— 那是文本内联（24KB 上限），不是上传。
10. **`agent.py:542` 已经在传 `files`** —— 一旦有工具产出附件，
    当前代码会直接抛错。实现上传时顺手把这个 bug 修掉。

但 browser target 正常。解决：`Target.attachToTarget` 或**新开 tab**。

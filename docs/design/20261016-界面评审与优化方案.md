## 二、总体判断

**这套壳的底子是好的，问题不在细节而在主体。**

做对了的（不重复设计稿的话，这里只记实测确认的）：

- **设计令牌单一定义**：`App.xaml` 是配色与样式的唯一来源，窗口代码从资源取，`Res()` 缺 key 直接抛。三处硬编码颜色的历史漂移已消除。
- **对比度是算过的，不是拍的**：`Ink 13.04:1 / InkSoft 6.05:1 / InkFaint 4.89:1`，语义色分 `*Fill`（图形 ≥3:1）与 `*Ink`（文字 ≥4.5:1）两套。注释里连"原为 #888780 = 3.36:1，不达标"都留着。
- **顶栏瘦身真的落地了**：实测顶栏右列只剩「健康胶囊 + 刷新 + 身份 + 设置」，约 210px；模型/思考/联网已挪进输入区芯片行。这是 v1 设计稿 P0 的完整兑现。
- **性能门禁是真的在跑**：`--perfcheck` 钉住消息块构造 1 ms/块（实测 0.04 ms），侧栏开合 100 ms 上限。这套自检机制在同类项目里罕见。
- **决策有据可查**：XAML 里大段注释解释"为什么不是 StackPanel""为什么不用 ToggleButton""为什么 `Children[i] = x` 会抛"。这是可维护性的真正来源。

**但是**：v1 设计稿的 P1（对话流分层）只做了一半 —— 思考块与工具卡片换皮了，**而对话流最主体的两条内容（用户消息 / 助手正文）一行没动**。而 P2（右栏常驻）、P3（设置重构）、P4（深色）全部未启动。

实拍截图里最刺眼的一幕：**连续 15 条 `> 开头`的消息，长得一模一样，分不出谁说的**。

## 四、问题清单（按严重度）

### P0-1 · 对话流没有角色区分（最严重）

**现象**：用户消息与助手正文在视觉上几乎同形 —— 都是纯文本行，唯一区别是用户消息多了个 `> ` 前缀、字重 SemiBold。

**证据**：
- 截图：连续 15 条 `> xxx` 行，扫视时是一整片灰，读不出轮次、读不出"谁在说"
- 源码 `MainWindow.xaml.cs:627`：`AppendConversation($"> {item.Text}", Ink, FontWeights.SemiBold);`
- 源码 `MainWindow.xaml.cs:1194`：助手正文 `MakeSelectable(item.Text, 13, Ink)` + `Margin(0,2,0,8)` —— 无容器、无角色标签、无底色
- v1 设计稿 P1 明确要求：「用户 `AccentSoft` 底 + `#D3E4F6` 描边 + 圆角 8 + 内边距 10/13；助手左侧 2px `Line` 竖线 + 左内边距 13」

**影响**：这是 agent 应用的主体内容区。用户回看一段 20 轮的对话时，无法快速定位"我提了什么、它答了什么"。当前靠 `>` 前缀做区分，是把结构信息压进了一个标点里。

### P0-2 · Markdown 完全不渲染

**现象**：助手输出里的行内代码、代码块、列表、粗体、标题、链接全部以裸文本呈现。

**证据**：
- 截图：`> \`apply_patch\` / \`multi_edit\`` —— 反引号原样显示
- 源码：`csproj` **零第三方依赖**，代码中无任何 Markdown 解析（`grep markdown|markdig` 无命中）
- 性能门禁样本里自己写着 `包含中文、English words、数字 12345，以及行内代码 \`local_cmd\``（`App.xaml.cs:431`）—— 说明设计者知道行内代码存在，但没渲染

**影响**：对 agent 应用是硬伤。工具名、文件路径、命令、代码片段 —— 这些恰恰是最需要等宽语义的内容，现在混在正文里读不出来。用户从对话里复制命令时，还会带上反引号。

**历史约束（必须尊重）**：本项目试过 `Emoji.Wpf.RichTextBox`，实测 **39.5 ms/块**，是原生只读 `TextBox`（0.04 ms/块）的 924 倍，被 `--perfcheck` 拦下并回退。**所以"换个 RichTextBox 全量渲染 Markdown"这条路是走不通的**（600 块列表会卡死）。

### P0-3 · 轮次没有边界

**现象**：一轮的开头只有一行 `── 第 N 轮 ──`（11px `InkFaint`），与正文同为纯文本行，几乎不可见。

**证据**：`MainWindow.xaml.cs:637`；截图里看不到任何轮次分隔。

**影响**：一次 run 22 次工具调用时，用户完全失去"这是一轮的第几步"的锚点。v1 设计稿诊断第 5 条原样存在。

### P1-4 · 监视器与对话不能同时看

**现象**：主区仍是「对话 / 监视器」二选一。

**证据**：`MainWindow.xaml:313` 两个按钮 + `MonScroll`/`ConvScroll` 靠 `Visibility` 互斥；`AppendMonitor`（`MainWindow.xaml.cs:1619`）只是把等宽 11px 文本行往 `MonPanel` 里堆。

**影响**：agent 执行器最需要"边说边做"同时可见 —— 工具正在跑时看不到它同时在说什么。v1 设计稿 P2 已识别，未动。

### P1-5 · 侧栏会话项信息过载

**现象**：208px 宽的侧栏里塞三层文字：标题（12px SemiBold）+ 副标题（10px `InkFaint`，如「378 轮 · 10-16 21:00」）+ 预览行（10px `InkSoft`）。

**证据**：截图里标题被截成「读取本地deepseek agent deskt...」；140% 字号下三层小字堆叠，行距已经很紧。

**影响**：预览行与副标题的信息密度重复（都在说"这条会话是什么"），而真正需要一眼看到的"什么时候聊的"反而最小。

### P1-6 · 「本地 / 网页版」不是分段控件

**现象**：两个裸 `Button`，选中态靠代码手改 `Foreground` / `FontWeight`。

**证据**：`MainWindow.xaml.cs:513-525`（`ApplyConvListView`）；截图里两个按钮看起来像并列动作，读不出"二选一"。

### P1-7 · 快捷键提示过长且被截断

**现象**：输入区右侧常驻一行提示，实测在 1830px 窗口下仍被窗口边缘切掉。

**证据**：截图右下「Enter 发送 · Shift+Enter 换行 · Ctrl+= / Ctrl+- 调整文字大小 · 文件拖入/粘贴即附件」—— 末尾文字顶到边框。

**影响**：一个被截断的提示比没有提示更糟 —— 它占着位置，却给不出完整信息。

### P1-8 · 没有空状态

**现象**：新会话或空对话时 `ConvPanel` 为空，一片空白。

**证据**：v1 设计稿组件表里有 `EmptyState`，代码里无实现。

### P1-9 · 设置对话框仍是单列长滚动

**现象**：780×800 里 7 个 `RowDefinition` 顺序堆叠：说明卡 → 占位符警告 → 文字大小 → 模板编辑框 → 预览 → 记忆 Expander → 操作条 → 状态条。

**证据**：`SettingsDialog.xaml`；想找「文字大小」要滚到中部，且不知道自己错过了什么。

### P2-10 · 输入区信息密度失衡

**现象**：芯片行是「左侧 3 枚芯片 + 右侧常驻提示」，中间一大段留白（截图里约 500px 空着），而右侧提示又被截断。

**影响**：空间给了留白，信息却在溢出。

### P2-11 · 「解除熔断」常驻

**现象**：`BtnReset`（「解除熔断」，86px）与「运行」并列常驻在输入区。

**证据**：`MainWindow.xaml:473`。

**影响**：一个极少触发的应急动作，占据了与主操作同等的视觉重量。v1 设计稿写的是「熔断时**才**出现」。

### P2-12 · 系统标题栏与自绘界面割裂

**现象**：窗口用系统默认标题栏（浅灰渐变 + 系统按钮），下面是自绘的米白极简界面。

**证据**：截图顶部 `DeepSeek Agent Desktop · 文字 140%` 一行是系统绘制。

**影响**：这是全窗口唯一"不是这套设计系统画的"部分，气质明显不同。v1 设计稿说"覆盖全部窗口"，但没覆盖标题栏。

### P2-13 · 等宽字体仍是 Consolas

设计稿建议换 Cascadia Mono（Windows 11 默认，字宽更规整），代码里 `private static readonly FontFamily Mono = new("Consolas");`（`MainWindow.xaml.cs:1282`）未改。

## 五、优化方案

**统一约束**（所有方案都必须满足，来自现有体系）：

1. 消息块构造 ≤ **1 ms/块**（`--perfcheck` 会拦）
2. 所有文字**可选中复制**（只读 `TextBox`，不用 `TextBlock`）
3. 新控件必须在创建时 `TextZoom.Fresh()` 登记，否则 `Ctrl+=` 静默失效
4. 配色**不改值**，只允许新增语义令牌
5. 层次靠 **1px 描边 + 极浅底色 + 字重**，不引入阴影与渐变
6. 顶栏宽度预算已耗尽，**不得往顶栏加东西**

---

### 方案 1（P0）· 对话流分层：把"谁在说"变成结构

**目标**：一眼分出用户 / 助手 / 工具 / 系统消息，且不牺牲密度。

**做法**（每条都落到 `MainWindow.xaml.cs` 的 `OnItemAdded`）：

| 条目类型 | 现状 | 改为 |
|---|---|---|
| 用户消息（`Goal`） | `"> " + 文本`，Ink SemiBold | `Border` 容器：`AccentSoft` 底 + `#D3E4F6` 描边 + 圆角 8 + 内边距 `10,7`；左对齐；去掉 `>` 前缀（结构由容器表达，不靠标点） |
| 助手正文（`Assistant`） | 裸文本 | 左侧 2px `Line` 竖线（`Border.BorderThickness="2,0,0,0"`）+ 左内边距 13；正文仍是只读 `TextBox`，**内容控件不变，只加容器** |
| 轮次（`TurnDivider`） | `── 第 N 轮 ──` 灰字 | 上边距 16 + 1px `LineSoft` 全宽横线 + 右上角 `第 N 轮` 11px `InkFaint` |
| 系统类（`Notice`/`Error`/`Gate`） | 彩色裸文本 | 保持裸文本（它们本来就是"旁白"，不该有容器）—— 但**间距加倍**，与对话内容拉开 |

**为什么容器用 `Border` 而不是重控件**：`Border + TextBox` 的构造代价与裸 `TextBox` 同量级（多一层 `Border`，约 0.01 ms），不会触碰 1 ms 阈值。这是唯一在性能预算内能做到"结构可读"的路子。

**关键取舍**：用户消息**去掉 `>` 前缀**。设计稿写的是"两者都左对齐，不用右对齐气泡"，那就必须有别的信号来区分 —— 底色 + 描边就是那个信号。同时把 `>` 从 `BuildConversationText()`（复制全文）里也去掉，改为 `[我]` / `[助手]` 标签，让复制出来的文本同样可读。

**验收**：`--selfcheck` 增一条断言 —— 断言用户消息的容器 `Background` 非透明、助手消息的容器有左边框；`--perfcheck` 消息块耗时仍 ≤1 ms。

---

### 方案 2（P0）· 富文本分级渲染：先做最高价值的两件事

**先说不能做什么**：全量 Markdown（换成 `RichTextBox` / `FlowDocument`）**在性能预算内不可行** —— 历史实测 39.5 ms/块，超阈值 39 倍。任何"引入 Markdown 库 + 富文本控件"的方案都会撞在 `--perfcheck` 上。

**再说该做什么**：agent 输出里真正需要富文本语义的只有两类，**先做这两类，其余保持纯文本**：

| 级别 | 元素 | 渲染方式 | 成本 |
|---|---|---|---|
| **L1（先做）** | 代码块 ` ``` ` | 独立块：`Sunken` 底（新增令牌 `#F2F1EE`）+ 圆角 6 + 等宽 11.5px + 右上角「复制」按钮 | 轻：一个 `Border + TextBox`，与现有工具卡片同构 |
| **L1（先做）** | 行内代码 `` `x` `` | 同一段落内无法混排（`TextBox` 不支持部分样式）—— **折中方案：把反引号去掉，整段改用等宽字体**，或按代码片段切分成多个 `TextBox` 用 `WrapPanel` 拼 | 中：需实测块数膨胀对性能的影响 |
| L2（二期） | 无序/有序列表 | 前置符号用 `•` / 序号，缩进 16px | 轻 |
| L2（二期） | 粗体 `**x**` | 同 L1 行内代码的切分方案 | 中 |
| L3（暂不做） | 表格 / 链接 / 图片 | 保持纯文本 | — |

**建议的落地路径**：先只做**代码块**（价值最高、成本最低、无性能风险）。行内代码的切分方案先在 `--perfcheck` 里量一遍块数膨胀倍数，再决定要不要做。

**为什么不建议引入 Markdig**：即使解析层用 Markdig（`Markdig.Signed.dll` 在本机另一个程序里已存在），渲染层仍是瓶颈 —— 解析出来的 AST 必须落到 WPF 控件上，而"每个富文本片段一个控件"正是性能陷阱。**瓶颈在渲染，不在解析**。

### 方案 3（P1）· 右栏常驻：让"说"和"做"同时可见

按 v1 设计稿 P2 落地，但**改一处**：

- 设计稿说右栏 300px、<1280px 默认收起。实测本机窗口 1830px 宽、140% 字号下，300px 右栏会挤压正文列（当前正文列已被 `SyncConvColumnWidth` 钉成固定宽）。建议**改为 260px**，并让正文列宽计算把它算进去。
- 监视器内容重构：现状是等宽文本行堆叠（`AppendMonitor`），**没有分组、没有级别、没有时间戳**。建议按「工具调用 / 闸门 / 引擎日志」分三组，每组可折叠，组头显示计数。工具调用与对话流里的工具卡片**共享同一个数据源**（`Host.Transcript`），只是呈现粒度不同 —— 不新增数据通道。

**风险**：这是唯一会**增加** XAML 复杂度的一期，建议方案 1、2 稳定后再做。

### 方案 4（P1）· 侧栏降噪

- **去掉预览行**（`PreviewLine`），把副标题升级为「时间 + 轮数」的主元信息（10px → 10.5px，`InkFaint` 保持）。
- 标题与副标题的**行距从 2px 收到 1px**，单项内边距 `9,5` → `8,5`，让 208px 宽里多容纳约一行标题字符。
- 侧栏宽度：设计稿写 236px，实测当前 208px 在 140% 下偏挤。**建议默认 220px**，并在 140% 以上字号时按比例微调（或直接让用户可拖拽 —— 但那是新功能，优先级低于前四条）。

---

### 方案 5（P1）· 分段控件 + 空状态

- **分段控件**：`本地 / 网页版` 换成 `Sunken` 底槽 + 2px 内边距 + 选中项 `Surface` 底的分段控件。注意设计稿写"选中项带极轻阴影"——**建议去掉阴影**，改用 1px `Line` 描边，与全窗口"零阴影"的既有约定保持一致。
- **空状态**：`ConvPanel` 为空时显示居中提示：一行 `InkFaint` 说明 + 一个主按钮（「开始新对话」或「读取网页版会话」）。实现上是一个 `Visibility` 与 `ConvPanel.Children.Count` 联动的占位块。

### 方案 6（P2）· 输入区重构

- **快捷键提示改两段式**：常态只显示 `Enter 发送 · Shift+Enter 换行`（约 140px），其余键位收进一个 `?` 图标按钮的 `ToolTip`。解决 P1-7 的截断。
- **「解除熔断」改为按需出现**：默认 `Collapsed`，仅在 `Breaker` 状态时出现（设计稿原意）。释放 94px。
- **附件按钮**：`＋文件` 目前是带文字的按钮，与三枚芯片的视觉重量不同。建议改成与芯片同规格（高 24、圆角 12）或降级为 24×24 图标按钮。

---

### 方案 7（P2）· 设置对话框左导航

按 v1 设计稿 P3 落地：左导航（提示词 / 显示 / 记忆 / 关于）+ 右侧内容区。780×800 的窗口尺寸可保持不变，但内容区不再需要纵向滚动。

**这一条可以延后** —— 设置是低频界面，而 P0 的两条影响每一次对话。

---

### 方案 8（P2）· 标题栏

若要彻底统一，需 `WindowStyle="None"` + `AllowsTransparency` + 自绘标题栏。**代价**：拖拽、双击最大化、贴边分屏、系统菜单、DPI 变化全部要自己实现，且 `AllowsTransparency` 会禁用硬件加速（对 600 块列表的性能是负面的）。

**建议**：**不做**。折中方案是把窗口标题简化（去掉「· 文字 140%」这段信息，它已经在设置里能看），让系统标题栏尽量少抢眼。

---

## 六、明确不做的事

| 不做 | 理由 |
|---|---|
| 全量 Markdown 渲染（RichTextBox/FlowDocument） | 39.5 ms/块的历史实测，性能预算不允许 |
| 引入阴影 / 渐变 / 大圆角 | 违反既有"零阴影"约定，且 WPF 下渲染成本高 |
| 改动配色值 | 每个值都过 WCAG AA，改一个要重算一整张表 |
| 自绘标题栏 | 收益是审美，代价是拖拽/贴边/DPI/硬件加速，不划算 |
| 往顶栏加任何控件 | 宽度预算已耗尽（MinWidth 历史 1000→1120） |
| 深色主题（本轮） | 条件已具备（配色语义化），但优先级低于 P0；且需要一套完整的深色值重新过 AA |

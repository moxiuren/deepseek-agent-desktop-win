## 一、风格取向的变化

| 维度 | v1（现行实现） | v2（参考图风格） |
|---|---|---|
| 色相 | 暖白（`#F7F7F5` 米白 + 暖灰描边） | **冷调**（`#EDF0F5` 浅灰蓝底 + `#E3E8F0` 描边） |

| 层次手段 | 1px 描边 + 极浅底 + 字重，**零阴影** | 描边 + 浅底 + **极轻阴影**（`0 1px 2px rgba(16,24,40,.04)`） |

## 三、组件映射（HTML → WPF）

| 设计稿元素 | WPF 落地 | 关键点 |
|---|---|---|
| 自绘标题栏 | `WindowStyle="None"` + 自绘 `Border` + `DragMove()` | **代价最大的一项**：拖拽、双击最大化、贴边分屏、系统菜单、DPI 变化全要自己实现，且 `AllowsTransparency` 会**禁用硬件加速** —— 对 600 块列表是负收益。建议**先不做**，只把标题文案简化 |
| 用户气泡 / 助手正文 | 用户：`Border`（`CornerRadius="12,6,12,12"`）右对齐；助手：`Border`（`CornerRadius=12`、无描边）通栏 | 两者都是**白底**（统一色系），靠**位置**区分角色；容器是 `Border`，**内容控件不变**（仍是只读 `TextBox`），可选中约束不破 |
| 助手头像（可自定义） | `Ellipse` 裁剪容器 + 内置 `Path` / 首字母 `TextBlock` / 用户图 `ImageBrush` | 三态切换；配置存 `ui-prefs.json`，**改后要遍历已渲染的消息块更新**（新消息用新头像）。`ImageBrush` 需 `Stretch="UniformToFill"` 防变形 |
| 任务列表（输入框上方常驻） | 独立于对话流的 `Border` + `StackPanel`，挂在输入区顶部 | **收起 = 一行**「当前第 N/M 步 + 当前步骤名」+ 2px 进度条；**展开 = 全部步骤**。**不属于对话流** —— 放进对话里会随历史滚走，长任务时看不到实时进度。数据源复用 `Host.Transcript`，不新增通道 |
| 代码块 | `Border`（白底 + 左侧 3px 蓝条）+ 等宽只读 `TextBox` + 复制按钮 | 解析层建议**自写轻量扫描**（只认 ``` 围栏），不引 Markdig —— 瓶颈在渲染不在解析 |
| 行内代码 | 按片段切分 → `WrapPanel` 拼多个 `TextBox` | **必须先量块数膨胀**（`--perfcheck`），切分粒度失控会直接撞 1ms/块阈值 |
| 工具卡 | 沿用现有 `ToolCardView`，换皮（`CornerRadius` 10、阴影、状态图标） | **折叠规则**：运行中默认展开 + 实时输出（`tool_progress` 每 1.5 s 刷新）+「实时输出」标记与光标；`done` 到达后自动折叠成一行。用户手动点过之后以 `Expanded` 标记为准，**自动行为不得把用户的选择顶回去**（现有实现已有该标记，直接复用） |
| 系统提示条 | `Border` + 图标 + 文本，内联进对话流 | 已有实现（`Gate`/`Breaker`/`Error`），换色即可 |
| 右栏三页 | `TabControl` 或三个 `RadioButton` + `Visibility` 切换 | 复用现有「一个字段 + 一个 Apply 方法」的互斥套路（见 `ApplyConvListView`） |
| 左栏导航 | 四个 `Button` + 手写高亮 | 同上一行，**不要用 `ToggleButton`**（v1 注释里已论证过会漂） |
| 分段控件（本地/网页版） | `Border` 槽 + 两个 `Button` | 现有 `ApplyConvListView` 的事件模型不动，只换外观 |
| 输入区 | `Border`（`CornerRadius=16`）+ `TextBox` + 芯片行 | 芯片沿用现有 `ChipCombo`/`ChipCheck`，加 `CornerRadius` |
| 圆形发送 / 取消按钮 | `Button` + `Ellipse`/`Border` 模板，`Width=Height=34` | 现有「同一格切换」的几何不变策略保留 |

## 四、落地时的硬约束（不满足就不要提交）

1. **消息块构造 ≤ 1 ms/块** —— `--perfcheck` 会拦。气泡多了一层 `Border`，代价约 +0.01 ms，安全；但**行内代码切分**要单独量。
2. **所有文字可选中** —— 气泡里的正文仍用只读 `TextBox`，不得为了排版退回 `TextBlock`。
3. **新控件必须 `TextZoom.Fresh()` 登记** —— 否则 `Ctrl+=` 对它静默失效（不报错）。
4. **阴影只允许一处**（`0 1px 2px rgba(16,24,40,.04)`），不得叠加多层 —— 600 块列表下阴影是实打实的渲染成本。
5. **顶栏不得再加控件**（预算已耗尽）。
6. **`--layout-audit` 必须 0 FAIL**，且审计要自报它是在什么字号下测的。

## 七、落地前的架构判断：要不要换框架

> 2026-10-16 22:35 · 回答「实践时是不是需要改框架」。结论基于对 `shell/` 与 `winui/` 的实际清点，非推测。

**结论：不换技术栈。WPF 留着，引擎与传输层一行不动。但必须做一次「渲染层拆分」—— 那不是改框架，是把已经违反项目门禁的东西归位。**

### 7.1 为什么不换栈

| 依据 | 事实 |
|---|---|
| 性能资产全在 WPF 上 | `--perfcheck` 的 1ms/块门禁、`TextZoom.Fresh()` 统一缩放登记、600 块列表的实测数据（切对话 900ms → 0.5ms）—— 换栈等于把这套全废 |
| 零依赖是刻意约束 | `csproj` 里**一个 `PackageReference` 都没有**。WinUI 3 必须引 `Microsoft.WindowsAppSDK`，这条约束当场破 |
| 设计稿要的东西 WPF 全能做 | 第三节映射表已逐条证明：气泡 = `Border` + 只读 `TextBox`，代码块 = `Border` + 等宽 `TextBox`，三栏 = `Grid` 加一列 |

### 7.2 `winui/` 那条路：冻结，不是否决

仓库里已有 WinUI 3 新壳骨架（`winui/WinUI3Desktop/`，分支 `feature/winui3-shell`）。README 自述状态：

- **尚未能编译运行** —— `dotnet build` 倒在 XAML 编译器 `WMC9999`（`App.g.i.cs` 访问被拒），根因未查明
- 第一道门 `dotnet workload install windows`（数 GB，需管理员）**未过**
- README 明确写着「在查清前不要装 workload / 不要钉死版本号」

所以它当前不是一条「可选的落地路径」，是一个**未解的问题**。在环境问题查清之前把设计稿压上去，等于把两个未解问题叠在一起 —— 出问题时无法二分定位是渲染逻辑还是 XAML 编译器。

**建议顺序**：WPF 版先把设计稿落地并验证（气泡、代码块、任务列表在真实 600 块负载下跑通），再拿这套已验证的交互去决定要不要移植。届时 `winui/` 的 WMC9999 若已解决，移植是「照着已知正确的目标重画一遍」，风险可控得多。

## 八、如果换成纯 HTML 界面

> 2026-10-16 22:44 · 回答「换成纯 HTML 界面呢 有什么好方案」。**含实测数据**，测量方法与局限见 8.2。

### 8.1 先分清「纯 HTML」的三种意思

这三个形态的成本差一个数量级，混在一起谈会得出错误结论：

| | 宿主 | 渲染 | 引擎 | 桌面形态 | 定位 |
|---|---|---|---|---|---|
| **A. WebView2 内嵌** | C#（保留） | 本地 HTML/JS | stdio（不动） | **保留**（窗口/任务栏/Alt-Tab） | 换渲染层 |
| **B. 浏览器直连** | 无 | 浏览器 | 需新增 WS 服务 | **失去** | 跨平台 / 远程访问 |
| **C. Electron / Tauri** | 重写 | Chromium | 重新对接 | 保留 | 换整个外壳 |

**关键区分**：C# 宿主当前承担三件事 —— 引擎进程生命周期（`EngineClient.Start` / `Kill(entireProcessTree)`）、stdio JSON-RPC 编解码、系统集成（凭据/配置/托盘）。这三件事**都不属于渲染层**。所以「只换渲染」和「连宿主一起扔掉」是两笔完全不同的账。

### 8.2 实测：Web 渲染 600 条消息的真实成本

**测量方法**：用设计稿 v2 的**真实 CSS**（提取 `<style>` 整块，含 `:root` 变量）生成 600 条消息（200 用户 + 300 助手含代码块 + 100 工具卡），7034 个 DOM 节点、93894px 内容高度。Chrome headless（`--headless=new --disable-gpu`，软件渲染，取 3 次中位）。生成脚本与测试页在会话临时目录，未入库。

| 指标 | WPF 现行门禁上限 | Web 基线 | Web + `content-visibility` |
|---|---|---|---|
| **600 条首屏渲染 + 布局** | 600 ms（600 × 1ms/块） | **134 ms** | **4.7 ms** |
| 每块成本 | 1.0 ms | 0.22 ms | 0.008 ms |
| 构建 DOM（fragment） | — | 10.3 ms | 13.4 ms |
| **追加 1 条（含强制布局）** | — | 0.9 ms | 0.4 ms |

`content-visibility: auto` + `contain-intrinsic-size: auto 140px` 是**一行 CSS 的浏览器内置虚拟化**，把首屏插入从 134ms 压到 4.7ms —— **28 倍**。这是 Web 方案唯一无可替代的杀手锏：WPF 要手搓虚拟化才能接近，浏览器原生就有。

**必须说明的三条局限**：

1. **headless 不含真实绘制（paint）**。但 `content-visibility` 的价值恰恰是跳过屏外元素的布局与绘制，所以这个数字方向正确、量级可信。
2. **`reflow60` 这个指标无效** —— 无 DOM 变更时浏览器直接返回缓存的布局值，所以测出来恒为 0.1ms。它不能代表滚动性能。
3. **真实滚动流畅度、合成层行为、以及 `content-visibility` 的滚动条跳动**（实测高度估算偏差：93894 → 84228，约 10%）**必须用真实窗口测**，headless 测不出来。

### 8.3 推荐方案 A：WebView2 内嵌

**本机就绪度**：WebView2 Runtime 已装 —— `155.0.4283.45`（`HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-...}` 确认）。

**推荐理由**：

1. **性能实测优于 WPF，不是妥协而是升级**（见 8.2）。
2. **保住 C# 宿主的全部资产** —— `AgentHost.cs`（2487 行）+ `EngineClient.cs`（428 行）**一行不改**，它们只管进程与协议，与 UI 技术无关。新增的只是一个桥：`CoreWebView2.WebMessageReceived` ↔ `PostWebMessageAsJson`。
3. **设计稿即实现** —— 这份 v2 HTML 直接是产品起点，**消除了「HTML → WPF 控件映射」这一整层损耗**。这是最大的结构性收益：第七节那张映射表现在可以直接作废。
4. **WebView2 用的就是 Edge 的 Chromium 内核**，所以上面 8.2 的数据就是它的性能基线，不需要另测。

### 8.4 迁移成本（按现有实现量清点）

| 项 | 现有实现量 | Web 侧对策 | 风险 |
|---|---|---|---|
| **中文输入法（IME）** | `MainWindow.xaml.cs` **14 处**引用 | WebView2 的 `compositionstart/update/end` 事件 | **高 —— 这是「能不能用」的问题，必须实测** |
| 拖拽 / 剪贴板 | **17 处** | WebView2 `DragDrop` + Clipboard API | 中 |
| `TextZoom` 统一缩放 | **27 处** | `:root{font-size}` + `rem` | **低 —— 比 WPF 简单得多** |
| 系统集成（窗口/托盘/DPI） | **5 处** | 留在 C# 侧不动 | 低 |
| `--perfcheck` 门禁 | 现有 C# 自检 | 改为测「追加 1 条的 JS 耗时」（方法见 8.2） | 中 —— 重建 |
| `--layout-audit` 门禁 | 现有 C# 自检 | 改为 WebView2 内跑 DOM 查询 | 中 —— 重建 |

**破零依赖**：从 0 个 `PackageReference` 变成 1 个（`Microsoft.Web.WebView2`）。分发时还多一个 Runtime 依赖 —— 本机已有，但别的机器要装（Win11 通常自带）。

### 8.5 不推荐的 B 与 C

**方案 B（浏览器直连）**：引擎是**纯 stdio**（28 个 Python 模块，无 HTTP server），要走这条路得给引擎加 WS 层。有利条件是 `websockets>=13` 已在 `requirements.txt` 里（目前只用于 `browser_login.py` 连 CDP）。但代价是失去桌面形态、且 C# 宿主管的进程生命周期要搬家。**它的定位是「跨平台 / 远程访问」，不是「更好的桌面 UI」** —— 如果目标是后者，选它是降级。

**方案 C（Electron / Tauri）**：Electron 体积 +200MB、Node 依赖树，与本项目「零第三方依赖」的刻意约束直接冲突；Tauri 体积小但引入 Rust 工具链，且两者都要重写宿主 + 重新对接引擎。收益不明确。

### 8.6 建议的第一步：一个可回退的 spike

**不要直接全量切换。** 先在现有 WPF 外壳里塞一个 WebView2 控件，加载设计稿 HTML + 灌 600 条真实消息，**只验三件事**：

1. **中文输入法能否正常工作** —— 14 处 IME 引用说明这里踩过坑，这是唯一可能导致方案作废的风险点。
2. **真实窗口下的滚动流畅度** —— headless 测不出来。
3. **跨边界通信延迟** —— 前端发一条 → C# 收到 → 引擎 → 回传，走完整链路测一次。

**不动现有渲染层，随时可回退。** 这三件事半天内能出结论，且结论是二值的：IME 能用 → 走方案 A；不能用 → 回第七节的 WPF 拆分路线。

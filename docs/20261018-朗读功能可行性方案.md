## 一、先否掉一个错误前提

开工前有个看似致命的障碍：**WebView2 只有 3 个英文语音、零中文**。

这个障碍**不存在**。因为它假设朗读走 `window.speechSynthesis`（浏览器把文本交给
操作系统语音包，同步吐 PCM）。实测证据表明网页版根本不走这条路：

| 检索项 | 在 `main.js`（1.59 MB）中的出现次数 |
|---|---|
| `speechSynthesis` | **0** |
| `SpeechSynthesisUtterance` | **0** |
| `decodeAudioData` | **0** |
| `MediaSource` | **0** |
| `tts` | 62 |
| `voice` | 39 |
| `朗读` | 15 |

而 `web-tts.9ddcbab81d.js`（38.8 KB，TTS 引擎本体）里，**只有服务端音频流才存在**的
概念一个不少：

```
decoderKind / firstFrameLatencyMs / sampleRate / underrunCount / rejected_code
WebCodecs  AudioDecoder({codec:"opus", sampleRate:24000, numberOfChannels:1})
WebAssembly opus 解码器兜底（chunk 61271）
```

Web Speech API 没有「解码器」「首帧延迟」「欠载」「配额」这些概念 ——
它是同步的本地合成，不存在网络流，也就无从「欠载」。

**推论**：壳里能不能说中文，只取决于**解码器**（WebCodecs 或 wasm opus），
与系统语音包无关。WebView2 Runtime 实测 **155.0.4283.62**，WebCodecs 早在
Chromium 94 就稳定，`opus` 解码支持从 100+ 起就没有回退。

## 二、完整协议（已逆向到可直接实现）

### 2.1 四个接口

```
POST /api/v0/auth/ticket          {"scope":"tts"}   -> ticket（36 字符）
GET  /api/v0/chat/tts/voices                        -> 音色列表
POST /api/v0/chat/tts/voice       {"voice_id": ...} -> 切换音色（全局偏好）
WSS  /api/v0/chat/tts/?chat_session_id=&message_id=&ticket=&mode=manual&format=opus
```

### 2.2 WS URL 的拼装顺序（不能错）

来自 `main.js` 模块 89791 的 `gY()`，源码如下：

```js
function a(e,t,n,r){
  let s=new URLSearchParams;
  for(let[e,n]of Object.entries(t)) s.set(e,n);   // ① streamParams 先
  s.set("ticket",n.ticket), s.set("mode",n.mode), s.set("format",n.format);  // ② 再固定三项
  void 0!==r&&(s.set("audio_id",r.audio_id),
               s.set("received_seq",String(r.received_seq)),
               s.set("played_seq",String(r.played_seq)));  // ③ 续播时才带
  let a=e.includes("?")?"&":"?";
  return "".concat(e).concat(a).concat(s.toString())
}
```

`streamParams` 的来源（`main.js`）：

```js
t.start({ getStreamParams: () => ({
    chat_session_id: e.sessionId,
    message_id: String(e.messageId)
  }), intentAt: r, playbackConfig: {...} })
```

注意 `message_id` 被 `String()` 包了一层 —— 服务端要的是字符串，不是 int。

### 2.3 帧格式

| 方向 | 类型 | 内容 |
|---|---|---|
| 服务端 → 客户端 | **二进制** | `4 字节大端 seq` + `Opus 负载` |
| 服务端 → 客户端 | 文本 JSON | 控制事件 |
| 客户端 → 服务端 | 文本 JSON | ack / abort / finish |

解析（`web-tts.js` 原文逻辑）：

```js
seq     = new DataView(buf).getUint32(0, false)   // 第三个参数 false = 大端
payload = new Uint8Array(buf, 4)
```

采样率 **24000 Hz 单声道**。

### 2.4 事件与错误码

服务端下发：

```json
{"event":"ready",  "audio_id": ..., "format":"opus"}
{"event":"finish", "code":0, "msg":""}
{"event":"finish", "code":5, "msg":"rate_limit_reached"}
{"event":"finish", "code":6, "msg":"no_content"}
```

错误码全表（模块 89791 的 `me`）：

| code | 名称 | 含义 |
|---|---|---|
| 0 | SUCCESS | 正常结束 |
| 1 | INTERNAL_ERROR | 服务端内部错误 |
| 2 | INVALID_INPUT | 参数不合法 |
| 3 | SERVICE_ERROR | 服务不可用 |
| 4 | QUOTA_EXCEEDED | 今日配额用尽 |
| 5 | RATE_LIMIT_REACHED | 触发限流 |
| 6 | NO_CONTENT | 该消息无可朗读内容 |
| 7 | UNSUPPORTED_LANGUAGE | 语种不支持 |
| 8 | VOICE_UNSUPPORTED_LANGUAGE | 该音色不支持此语种 |
| 9 | CONTENT_FILTER | 内容被过滤 |

客户端上行：

```js
{"event":"ack",    "received_seq":N, "played_seq":M}
{"event":"abort",  "reason":"..."}
{"event":"finish"}
```

`ack` 是**流控**，不是可选的心跳：服务端靠它判断客户端消费到哪一帧，
不回 ack 会把缓冲区打满然后断流。


**这组数据是成功的证据，不是失败**：

对照实验（假 `message_id`）返回 `code: 6 no_content` —— 同样是真实业务响应，
进一步证明协议正确：服务端能区分「消息不存在」和「限流」，说明它真的在读参数。

## 四、三条实现路线

### 路线 A（推荐）：**引擎侧全包，前端只做按钮**

```
app.js 朗读按钮  --{t:"tts", seq, messageId}-->  WebBridge
                                                    |
                                              AgentHost.TtsAsync()
                                                    |
                                     engine/gad_engine/tts.py
                                       ① POST /auth/ticket
                                       ② websockets 连 WS
                                       ③ 收 opus 帧 → PyAV 解码 → PCM
                                       ④ 写入 WAV / 喂 waveOut
```

**优点**

- 复用引擎已有的 TLS 指纹（`curl_cffi` chrome150）、UA、locale —— 与其它请求一致
- token 不出引擎进程（前端现在根本拿不到 token，见下）
- 限流/配额错误在 Python 侧统一处理，前端只需显示文案

**代价**

- 新增依赖 `av`（PyAV，约 40 MB，含 FFmpeg）或 `opuslib`（需系统 libopus）
- 播放要跨语言：要么 Python 侧推 PCM 到 Windows（`winsound` 只支持 WAV 文件），
  要么把解码后的 PCM 回传前端

### 路线 B：**前端全包，宿主只发 ticket**

```
app.js  --{t:"ttsTicket", messageId}--> WebBridge → AgentHost
         <--{t:"ttsTicket", ticket, sid, mid}--
app.js  new WebSocket(...)  → WebCodecs AudioDecoder → AudioContext
```

**优点**

- 解码播放零额外依赖 —— WebCodecs + AudioContext 是 WebView2 自带能力
- 代码量最小：前端约 200 行，宿主约 40 行

**必须跨过的两道墙**

1. **CSP `connect-src 'none'`** —— `index.html:23` 明写不发任何网络请求。
   要开一条 `connect-src wss://chat.deepseek.com`，并且**必须在注释里
   把「为什么这里破例」写清楚**（该文件现有注释的精神就是：每一条放宽都要能自证）。
2. **ticket 会短暂进入 JS 内存** —— ticket 是**一次性、短时效、只对单条消息有效**
   的凭证，不是账号 token。风险可接受，但要在代码注释里标明这一点，
   免得以后有人以为「前端已经能拿凭证了」而顺手把真 token 也传下去。

**为什么我倾向 B**：它把「能不能解码」这个唯一的不确定性交给浏览器
（WebView2 155 必然支持），而 A 引入 40 MB 原生依赖只为解 Opus —— 不划算。
真正的复杂度在播放管线（预缓冲、欠载重连、ack 流控），这部分无论 A 还是 B 都要写，
写在哪边都一样。

### 路线 C：**服务端中转**（不推荐）

引擎下载音频存 WAV，前端用 `<audio src="...">` 播。
最稳，但**完全失去流式**：长回答要等全部合成完才出声。网页版的体验优势正是
「边合成边播」，放弃它等于放弃这个功能的全部价值。

## 五、路线 B 的改动清单（精确到文件）

### 5.1 引擎侧：新增 `engine/gad_engine/tts.py`

```python
"""TTS 控制面 —— 只签发 ticket 与音色列表，音频流由前端直连。

为什么不在这里传音频：Opus 解码在 WebView2 里是原生能力（WebCodecs），
Python 侧要多装 40 MB 的 PyAV 才能做到同样的事。把流交给浏览器，
引擎只保留「鉴权」这一件它本来就在管的事。
"""
```

需要三个函数：

| 函数 | 作用 | 返回 |
|---|---|---|
| `fetch_ticket(client)` | `POST /api/v0/auth/ticket {scope:"tts"}` | `str`（36 字符） |
| `list_voices(client)` | `GET /api/v0/chat/tts/voices` | `list[Voice]` |
| `set_voice(client, voice_id)` | `POST /api/v0/chat/tts/voice` | `bool` |

**注意**：`fetch_ticket` 必须在**引擎已有会话上下文**里调用，且 `chat_session_id`
必须属于当前账号 —— 否则服务端返回 `INVALID_INPUT`。项目里
`AgentHost.EnsureCurrentSessionBelongsToAccountAsync()`（`AgentHost.cs:1423`）
已经在做这件事，复用它。

### 5.2 宿主侧：`WebBridge.cs` 加两个 case

```csharp
case "tts":
    // 前端请求朗读某条消息：签发 ticket 并把拼 WS 所需的三个值回传。
    // 回传的是 ticket（一次性、单消息有效），不是账号 token。
    var mid = Str(root, "messageId");
    var (sid, ticket) = await _host.PrepareTtsAsync(mid);
    Send(new { t = "ttsReady", req, sid, messageId = mid, ticket });
    break;

case "ttsVoices":
    Send(new { t = "ttsVoices", req, voices = await _host.ListTtsVoicesAsync() });
    break;
```

**关键**：`req` 必须原样回传 —— 前端用 `req` 匹配请求/响应（现有所有 case 都遵守这个约定）。

### 5.3 前端侧：`app.js` 加播放管线

**挂载点**：`msgBot()`（`app.js:441`）—— 目前只渲染头像 + 气泡，加一个按钮组即可。
但要**只对最终消息挂**（`it.streaming === false`），流式中的半截内容不提供朗读。

**新增文件 `tts.js`**（不塞进 app.js —— 后者已 2417 行，逼近 500 行红线的问题
在项目里已有先例，新功能应当独立成文件）：

```js
// 解码链：Opus 帧 → AudioData → AudioBuffer → AudioContext
const dec = new AudioDecoder({ output: onPcm, error: onDecErr });
dec.configure({ codec: 'opus', sampleRate: 24000, numberOfChannels: 1 });
```

三条必须写对的细节：

1. **ack 要跟着播放走，不是跟着收到走**
   `received_seq` = 已收到的最大 seq；`played_seq` = 已播出去的 seq。
   两者分开正是为了让服务端知道客户端是「网络慢」还是「播放慢」。
2. **欠载恢复要带 `audio_id` / `received_seq` / `played_seq`**
   这是 `gY()` 的第三个分支（`void 0!==r`）—— 续播时重连不是重新开始，
   服务端靠这三个值知道从哪继续。
3. **预缓冲**：`tts_prebuffer_ms` 没到之前不要 `AudioContext.resume()`，
   否则开头几帧会听到断续。

## 六、代价与风险（必须如实列出）

| 项 | 说明 | 严重度 |
|---|---|---|
| **配额** | 实测已触发 `code 5`。TTS 有独立的今日限额（`QUOTA_EXCEEDED=4`） | 高 —— 高频朗读会撞墙 |
| **非公开接口** | `/api/v0/chat/tts/*` 未在文档中出现，DeepSeek 改协议就断 | 中 —— 与项目其它 RPC 同一风险等级 |
| **CSP 破例** | 要开 `connect-src wss://chat.deepseek.com` | 低 —— 但注释必须写清理由 |
| **风控** | 朗读是账号行为，与发消息同源。频繁朗读可能计入异常 | 中 —— 与现有发送同风险 |
| **WebCodecs 兜底** | 极老 WebView2 可能没有 `AudioDecoder`，需要 wasm opus 兜底 | 低 —— 本机 155 已确认 |

**不能做的事**：不要为了「测试充分」高频打 TTS 接口。已限流过一轮，
再打就是主动招风控 —— 与用户「拟人操作、不能因测试导致封号」的要求直接冲突。

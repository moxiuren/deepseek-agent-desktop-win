#### 「停止生成」的语义澄清（本轮查证）

盘点文档原文是「两个 transport 都没有中断通道」，这句话**没错**，但容易被读成「停止功能不存在」。
实际分两层：

| 层 | 有没有 | 行为 |
|---|---|---|
| **硬中断** | **没有** | SSE 读流无法中途掐断，服务端可能仍在生成 |
| **协作式取消** | **有** | `agent.py:764` 的 `if outcome.cancelled:` 分支：停止累积、标记 `stop_reason = "cancelled"`、保留已生成的 `final_text` |

旅程 3 实测五轮，`final_text` 一律保留（2292 字 / 102 字 / 0 字三种情形都正确）。
**所以「停止」对用户是有效的**——用户看到的内容立刻停住；
只是它省不了服务端的算力，也省不了额度。

## 2. 本轮（2026-10-18 晚）做了什么

### 2.1 修复：`show_thinking` 的误导性提示

**改了什么**
`shell/DeepSeekAgent.Desktop/AgentHost.cs` 的 `SetChatAsync`。

原代码把四个参数合并成一句通知。但四者的语义不同：

| 参数 | 语义 | 影响上游 |
|---|---|---|
| `temporary` | 临时对话 | 是 |
| `extended_thinking` | 上游是否思考 | 是 |
| `search_enabled` | 是否联网 | 是 |
| **`show_thinking`** | **本地是否显示思考原文** | **否** |

引擎侧 `agent.py:2484` 注释写得很清楚：「纯本地显示开关，不改上游行为」。

把显示开关说成「已切换会话形态」，用户会以为**自己切换了对话类型**。
已累积 9 条误导性通知。

现在拆成两条互斥分支：会话形态说形态，显示开关只说自己影响显示。

**怎么验证的**
```
dotnet build  →  0 Warning / 0 Error
重启壳 → PID 18780
实测切换 → 只出 1 条「已隐藏思考过程（只影响本地显示，不影响上游是否思考）」
```

**未验证 / 存疑**
无。

### 2.2 新建门禁：Web 壳双向消息契约

**为什么需要**

WPF 壳的前端是 C# 写的，按钮直接绑方法，**编译器会拦下拼错的成员名**。
Web 壳的前端是 JS，跟宿主之间只有字符串：

```
JS:  send({ t: 'switchConv', id: ... })     → postMessage
C#:  switch (type) { case "switchConv": ... }
```

字符串拼错，编译器一个字都不会说。用户看到的是「点了没反应」——
没有异常、没有日志、没有红色，**只有沉默**。

这是 Web 壳独有的缺陷类别，所以必须单独设闸。

**两个方向都查**

| 方向 | 后果 | 严重度 |
|---|---|---|
| 前端发了宿主不认识的 `t` | 消息石沉大海 | 高（功能完全无效） |
| 宿主发了前端不认识的 `t` | 数据到了但界面不更新 | **更高**（用户以为功能坏了，实际数据是好的） |

**实测结果**

```
宿主接受 31 种 · 前端发送 28 种
宿主发送 16 种 · 前端接受 16 种

[方向一] 前端发送 → 宿主接受   [通过] 无孤儿消息
[方向二] 宿主发送 → 前端接受   [通过] 无孤儿消息

[参考] 推送型（宿主主动发，前端不该主动请求）
         · idLabel · models · refreshConvs

[通过] 双向契约一致
```

**门禁本身的三次纠错**

| 版本 | 误报 | 根因 | 修法 |
|---|---|---|---|
| 1 | 5 个假孤儿（err/files/ready/idres/idstate） | 全是**注释里**的说明文字 + `mock.js` 模拟宿主的 `fire()` | `strip_comments()` + 排除 mock.js |
| 2 | 入站集合被撑到 14 种无关项 | 全局扫 `case 'x'` 把 transcript kind 分派也算进来 | 只扫 `handle(m)` 函数体 |
| 3 | `models` 被误判为死代码 | 没看出它是宿主推送 | 加 `PUSH_ONLY` 集合 |

第 3 版值得单独说：我一度认定是真缺陷，准备去修 ——
实际 `WebBridge.cs:262` 在 `case "hello"` 里已经 `_ = RefreshModelsAsync()`。
**推送型消息不该要求前端主动发。**

**运行时交叉验证**（静态门禁必须配一条运行时证据）：
去页面看 `selModel`，实测 2 个选项、当前选中 `default` —— 宿主确实推了、前端确实画了。

#### `content-visibility` 的 A/B 裁决

CSS 注释声称「600 块首屏 134ms → 4.7ms」。本轮实测：

| 场景 | 开启 CV | 关掉 CV | 结论 |
|---|---|---|---|
| 批量插入 600 块 · 强制同步布局 | **22.3 ms** | 304.1 ms | **快 13.6 倍，收益真实** |
| 滚动帧间隔中位 | 16.7 ms | 16.7 ms | 无差异 |
| 滚动最长帧 | 19.3 ms | 17.0 ms | 开启**略差** 2.3ms |
| 滚动 >50ms 卡顿帧 | 0 | 0 | 都不卡 |

**判读**：CV 省的是「一次性灌大量块」的成本，不是滚动成本。
**规则该留，但注释里的「134→4.7ms」不准确** —— 实测首屏 30.8ms，
且分批铺开之后首屏本来就不含全部 600 块。

### 3.3 被实测否决的三项「优化」（重要）

这三条原本都在待办清单里，探针跑完后**判定为负收益或不成立**：

| 项 | 原设想 | 实测 | 结论 |

## 8. 结论

### 做对了什么

1. **性能优化有实测支撑，不靠直觉。** 四项「优化」被探针否决 —— 这比做对四项更有价值，
   因为它证明了这个项目的优化判断是可证伪的。
2. **降级行为做到 10 档全对**，且六档优先级链验证有效。大多数产品在这个环节是「有个错误提示就算完」。
3. **PoW 预取把用户等待从 8.2 秒压到 0 秒**，且判据设计得严（命中时 `pow_ms` 必须严格为 0）。
4. **门禁会失败。** 对比度门禁反向注入能报 26 处 FAIL，契约门禁的三次纠错说明它真的在判定，
   不是永远返回绿色。

### 最大的三个风险

1. **T1 降级通道是空壳。** 熔断层以为自己在保护用户，实际上降级即停摆。
2. **Web 壳的可访问性是退化的。** 会话列表在 UIA 里只是两段文字，键盘和屏幕阅读器都够不着。
   这是从 WPF 壳迁移到 Web 壳时丢掉的能力，不是「还没做」。
3. **沉默失败。** 契约类缺陷不产生任何可见信号。门禁能挡住回归，但挡不住「本来就没接上」的新功能。

### 下一步建议（按优先级）

1. **补 T1 降级通道**（T-26）—— 这是唯一的「生死开关」，其它都是体验问题
2. **给 Web 壳加设置页** —— 顺带把深色主题、权限档位接进去
3. **会话列表补语义** —— `role="button"` + `tabindex` + `aria-label`，改动量很小
4. **把契约门禁并入统一自检** —— 目前手动跑，容易被忘
5. 第一批纯本地优化（T-5 / T-6 / T-7）—— 零风险，可随时做

## 零、先厘清：为什么做这个

不是「为了追 PTC 而做」。真正的问题是**当前所有命令以当前用户全权限运行**：

- `safety.py` 只拦「明显灾难性」的命令（format / rm -rf /），是**启发式**的
- 模型可以 `Remove-Item` 任何它有权删的东西
- 一次提示词注入 → 一个循环 → 一批文件没了

沙箱是**从「靠规则拦」升级到「靠隔离限」**。PTC 只是它顺带解锁的能力。

---

## 一、目标与非目标

### 目标
1. **限制文件系统访问范围** —— 命令/脚本只能在声明的目录内读写
2. **限制资源** —— CPU 时间、内存、子进程数、运行时长
3. **可观测** —— 脚本做了什么（读了哪些文件、起没起进程）有记录
4. **不破坏现有体验** —— 默认行为不变，沙箱是**可选加固**

### 非目标（诚实边界）
1. **不是对抗恶意模型的安全边界** —— 模型不是攻击者，是可能犯错的执行者。
   目标是「限制爆炸半径」，不是「防住有能力的攻击者」
2. **不做 OS 级强隔离** —— 不引入 Hyper-V / 容器（成本高、Windows 上体验差）
3. **不替代 `safety.py`** —— 两者互补：safety 拦「明显危险」，沙箱限「能力范围」

## 二、Windows 上能用的隔离手段（现实盘点）

| 手段 | 能力 | 成本 | 本项目适用性 |
|---|---|---|---|
| **Job Object** | 资源限制（内存/CPU/进程数）、整组杀进程 | 低 | ✅ **首选** —— 标准库 ctypes 可调 |
| **低完整性级别 token** | 禁止写高完整性位置（如系统目录） | 中 | ⚠️ 可选 —— 需 CreateRestrictedToken |
| **路径白名单（Python 层）** | 拦 open() / write 到范围外 | 低 | ✅ **必做** —— 但只在 Python 脚本有效 |
| **工作目录锁定** | 命令 cwd 固定 | 零 | ✅ **已有** |
| **AppContainer** | 真隔离（网络/文件系统） | 高 | ❌ 太重，Windows 上坑多 |
| **Hyper-V 容器** | 最强隔离 | 极高 | ❌ 不现实 |

**结论**：走 **Job Object（资源）+ Python 层路径白名单（文件）+ 子进程（隔离运行环境）** 的组合。这是 Windows 上「性价比最高」的一档。

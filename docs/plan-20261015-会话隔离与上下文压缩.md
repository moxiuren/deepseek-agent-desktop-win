## 零、先纠正一个前提（实测数据，不是推断）

需求原文说「多回合之间不会真正切换到对应会话的页面，而是所有会话共用一个窗口」。
**这条在服务端层面不成立** —— 本轮用真实传输层实测（`tools/verify_session_isolation.py`，12/12 通过）：

| 验证项 | 实测结果 |
|---|---|
| 对话 A 的 chat_session | `<session-A>` |
| 对话 B 的 chat_session | `<session-B>` |
| 两者是否相同 | **不同** |
| 切回 A 后问「刚才让你记的数字是几」 | 答 **`731`**（A 的数字），**不含** `942`（B 的数字） |
| A 的服务端消息树 | `#1(parent=None) → #2(parent=1) → #3(parent=2) → #4(parent=3)` 链完整 |

**结论：隔离与续接机制本身已经工作。** `SessionManager` 虽只有一个实例，但切对话时
`agent.py:614 load_conversation()` 会同时换掉 `self.conversation` 与 `self.session.meta`
（`session.restore()` 是**共享对象引用**，不是拷贝），传输层据此换 `chat_session_id` +
`parent_message_id`，服务端因此落在不同会话树上。

### 那「共用一个窗口」的观感从哪来

三条真实成因，按可能性排序：

1. **切对话只重放本地消息，不读服务端**（`AgentHost.cs:743 ReplayConversation(conv)`）。
   本地记录是「用户输入 + 助手正文」的简版；工具调用中间过程、思考内容、
   以及在**网页版里聊过的内容**都不在本地。切过去看到的是删减版历史 ——
   观感上就像「同一个窗口里的另一段内容」，而不是「另一个真实的会话」。
2. **每轮重发 `_bootstrap_prompt`**（`agent.py:298`）。首轮发「系统提示词 + 任务」，
   第 2 轮起发「工具结果」（`agent.py:523`）。服务端会话里第 1 条 USER 消息的
   `content` 就是**完整系统提示词** —— 在网页版里逐条点开看，每个会话开头都长得一样。
3. **界面本身只有一个对话流控件**（`ConvPanel`），切对话是重放填充，不是独立视图。

⇒ 下面三个需求里，**第 1 条（真切换）是「把它做实、做可验证」，第 2、3 条是真缺口。**

## 一、本轮新拿到的服务端事实（全部实测）

### 1.1 两个此前从未探测过的接口

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/v0/chat_session/fetch_page` | **GET** | 会话列表（`count` 可选） |
| `/api/v0/chat/history_messages` | **GET** | 某会话完整历史（`chat_session_id` 必填） |
| `/api/v0/users/current` | GET | 当前账号 |

判定依据：`POST` 版本回 **HTTP 405 + `allow=GET,HEAD`**（API 层 JSON）；
而未注册路径会被 SPA 兜底吞成 `200 + HTML`。两者可区分 ——
这条判据已写进 `tools/probe_history_api.py` 的注释。

### 1.2 历史消息结构

```
data.biz_data
├─ chat_session   { id, title, seq_id, current_message_id, is_empty,
│                   version, inserted_at, updated_at, pinned, model_type }
├─ chat_messages  [ ... ]
├─ cache_control  "REPLACE"
└─ cache_reset_at 1792072078

chat_messages[i]  { message_id(int), parent_id(int|None), role(USER|ASSISTANT),
                    status(FINISHED), accumulated_token_usage(int),
                    thinking_enabled, search_enabled, model,
                    fragments[], has_pending_fragment, ... }

fragments[j]      { id, type(REQUEST|RESPONSE|THINK|SEARCH), content,
                    references?, stage_id? }
```

**三个关键点：**

- **`current_message_id` = 末条消息的 `message_id`**（实测相等）。
  这是**续接锚点** —— 切回旧会话时，`parent_message_id` 就该用它。
- **`message_id` 是 int，不是 uuid**。而 `SessionMeta.rid` 是 `str`。
  类型约定必须在映射层统一，否则 `int(x) if x.isdigit() else None`
  （`deepseek_rpc.py:846`）会**静默降级成新 root** —— 上下文断掉且无任何报错。
- **`accumulated_token_usage` 是唯一的真实 token 数据**。
  SSE 流里**没有** usage（`transport/base.py:91 TurnOutcome` 无该字段），
  所以实时压缩判断只能靠本地估算，或定期回读服务端。

- 本地 `rid` 因故丢失/过期 → `parent_message_id` 变 `None` → 服务端新建 root →

## 三、需求 2 —— 进入会话时读取服务端历史

这是**真正的缺口**。当前 `ReplayConversation` 只吃本地 `conv.messages`。

### 3.1 新增模块 `engine/gad_engine/remote.py`

```python
def normalize_history(biz_data: dict) -> tuple[list[Message], str]:
    """把服务端 chat_messages 映射成本地 Message 列表 + 校正后的续接锚点。

    映射规则：
      role   USER → "user"   ASSISTANT → "assistant"
      text   fragments 里 type ∈ {RESPONSE, REQUEST} 的 content 按序拼接
             （THINK / SEARCH 片段丢弃 —— 正文里混进 "Found 12 web pages"
               是实测踩过的坑，见 transport/base.py:98 的注释）
      rid    str(message_id)          ← 统一成 str，与 SessionMeta 约定一致

```

### 3.2 系统提示词剥离（必须做，否则历史不可读）

服务端第 1 条 USER 消息的 `content` 是 `_bootstrap_prompt()` 的产物，
格式固定为：

```
<渲染后的系统提示词>

# 任务
<用户真实输入>
```

`agent.py:950` 的 `f"{prompt}\n\n# 任务\n{goal}"` 保证了 `\n\n# 任务\n` 这个**稳定分隔符**。

```python
TASK_SEP = "\n\n# 任务\n"

def split_system_and_task(content: str) -> tuple[str, str]:
    """返回 (系统提示词, 用户输入)。没有分隔符时退化为 ("", content)。"""
```

**同时**：首轮那条 USER 消息在界面上应显示为**系统提示**（可折叠、默认收起），
而不是伪装成用户说的话。

### 3.3 合并策略（本地元数据不能丢）

服务端是**文本权威源**，本地是**元数据权威源**。合并规则：

- 以服务端消息序列为骨架（它含网页版里聊过的内容，本地没有）
- 每条 assistant 消息，若本地存在 `rid` 相同的记录，则**继承**其
  `tool_calls` / `thoughts` / `stop_reason` / `error`
- 本地有、服务端没有的消息（例如某轮发送失败、从未落服务端）→ **保留在末尾**，
  并标记 `local_only=True`（这是真实发生过的事，删掉就是伪造历史）

## 四、需求 3 —— 上下文压缩与续接

> **✅ 已实现（2026-10-15）**，但**触发方式与本节设计不同**：
> 最终做成了**用户手动**（界面「接力新会话」按钮 + `auto_rotate=False`），
> 不是阈值自动 —— 依据是需求方后来的判断「把切换对话的选择交给用户」。
> 摘要也**改为发进当前会话**（不是本节 4.2 写的独立会话），
> 理由见 `docs/evidence/20261015-接力换会话.md` 第二节。
> 下文保留原始设计，供对照。

### 4.1 触发策略（三层，任一命中）

| 依据 | 阈值（默认） | 数据来源 | 成本 |
|---|---|---|---|
| 轮数 | `trigger_turns = 20` | 本地 `conv.turn_count` | 零 |
| 字符数 | `trigger_chars = 40000` | 本地消息长度求和 | 零 |
| 真实 token | `trigger_tokens = 48000` | 回读 `accumulated_token_usage` | 一次 GET |

**为什么三层都要**：轮数是廉价近似；字符数是修正（长工具输出会撑爆）；token 是唯一真实值。
单用轮数会漏掉「一轮返回 3 万字」的情况。

> 轮数默认 20 与 `PacingConfig.max_turns_per_session`（默认 25）**联动设计**：
> 摘要先于轮换发生，这样轮换时摘要已就绪，新会话第一轮就能带上。

### 4.2 摘要生成（关键决策：**发到独立会话**）

**不能**把总结请求发进当前会话 —— 那会在对话树里留下一条「请总结以上内容」，
既污染上下文，又会成为下一轮的 `parent`。

设计：

```python
async def build_summary(rt, conv, policy) -> str:
    """用一个**一次性会话**做总结，用完即弃。

    - 新建 SessionMeta()（cid 为空）→ transport 自动 _create_session
    - 总结完成后这个 chat_session 就成孤儿，不影响主会话树
    - 复用同一个"总结专用会话"可减少垃圾会话数（见 4.5 权衡）
    """
```

总结 prompt 由 `compact.py::build_summary_prompt()` 生成，要求模型输出固定结构：
`【目标】【已确认事实】【未决问题】【关键路径/命令】` —— 结构化摘要比自由文本更抗遗忘。

### 4.3 注入位置

`agent.py::_bootstrap_prompt()` 增加摘要段落，位置在 **memory 之后、`# 任务` 之前**：

```
<系统提示词>
<长期记忆>
# 更早对话的摘要（截至第 N 轮）
<摘要正文>
# 任务
<用户输入>
```

因为 `_bootstrap_prompt` 是**每轮现算**的（`agent.py:298`），
所以**轮换后新会话的第一轮自动带上摘要** —— 这正好满足需求里
「自动开启新会话时把摘要一并发送上去，从而延续对话」。

### 4.4 改动点

| 文件 | 改动 |
|---|---|
| `engine/gad_engine/compact.py` | **新增**：`CompactPolicy` / `should_compact(conv, policy)` / `build_summary_prompt(conv, policy)` / `render_summary_block(summary, upto_turn)` |
| `engine/gad_engine/config.py` | 新增 `CompactConfig`（`enabled` / `trigger_turns` / `trigger_chars` / `trigger_tokens` / `keep_recent` / `max_summary_chars`），挂到 `EngineConfig.compact` |
| `engine/gad_engine/store.py` | `Conversation` 加 `summary: str = ""`、`summary_upto: str = ""`（已压缩到的 message_id）、`summary_at: float = 0.0` |
| `engine/gad_engine/agent.py` | `_bootstrap_prompt` 注入摘要块；<br>`run()` 末尾（`_record_assistant` 之后）调用 `_maybe_compact()`；<br>`_maybe_compact` 走 `self.gates` 节流（**不能绕过闸门**） |

### 4.5 必须写进代码注释的三个风险

1. **压缩本身要消耗一次 completion 请求**。项目已实测「17 分钟内 9 次 completion
   就撞服务端 68 秒生成超时」（`PacingConfig` 文档字符串）。所以压缩请求**必须**走
   `PacingGate`，且阈值不能设得太低。
2. **垃圾会话**。每次压缩若新建 chat_session，账号历史里会积累孤儿会话。
   缓解：复用**一个**固定的「摘要工作区」会话（存 `compact.session_id` 于配置），
   每次压缩前清空它 —— 但这又需要 delete 接口（**未探测**）。
   退路：接受少量垃圾会话，或改用本地规则摘要（质量低但不发请求）。
3. **摘要即丢失**。压缩不可逆 —— 被压掉的原文必须**仍留在本地**
   （`conv.messages` 不删），摘要只是**注入用**的副本。
   这样用户翻旧记录时不会发现内容凭空消失。

## 七、待你确认的一件事

实测显示服务端隔离是成立的。如果你观察到「共用一个窗口」的**具体现象**是下面哪一种，
请告诉我，方案的重点会不一样：

- **A** 切对话后，对话流里看到的历史比实际少（缺网页版聊过的内容）→ 重点做需求 2
- **B** 在 DeepSeek 网页版里，所有消息都进了同一个会话 → 那是另一个问题，需要重新查
- **C** 两个对话里问同一件事，模型答出了另一个对话的内容 → 隔离真有 bug，需要复现
- **D** 界面本身想要「每个对话一个独立视图/窗口」→ 这是 UI 重构，与引擎无关

**在拿到这个确认之前，第 1、2 阶段（服务端历史读取）可以照做** ——
它无论哪种情况都需要。
